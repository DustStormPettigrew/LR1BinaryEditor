## Sequential acceptance procedure

### 1. Startup and a valid real-corpus file

1. Run the exact launch command above.
2. Confirm one main window opens without a crash, unhandled-error dialog, or second process window.
3. Confirm `corpus-valid.CDB` opens in one tab.
4. Confirm the status bar reports `ValidSemantic`, `Tokenized`, a source-evidence value, and nonzero source/expanded byte counts.
5. Confirm the yellow issue banner is hidden and Save, Save As, Validate, and Export JSON are enabled.

Expected: the real CDB is parsed through LibLR1 and is writable; no source file is changed merely by opening it.

### 2. Syntax highlighting, folding, and line numbers

1. In `corpus-valid.CDB`, confirm a visible line-number margin starts at line 1 and continues while scrolling.
2. Confirm token IDs, strings, numbers, and comments are visually distinguished by syntax color.
3. Find a brace-delimited section with a folding marker in the margin.
4. Click the marker once and confirm the section collapses; click it again and confirm the original text returns.
5. Scroll and resize the window; confirm the line-number margin, text, and fold markers remain aligned.

Expected: highlighting, brace folding, and line numbers are active and stable.

### 3. Edit, gate, validate, diff, undo/redo, and Save As

1. Open `editable-valid.CDB` with File > Open.
2. Confirm its text is exactly this structure:

   ```text
   0x28    // Scene files
   [1]
   {
       "world"
   }
   ```

3. Replace `"world"` with `"earth"`.
4. Confirm the tab and window title gain `*`, the banner says `Candidate needs validation`, and Save, Save As, and Export JSON become disabled.
5. Press Ctrl+Z. Confirm `"world"` returns. Press Ctrl+Y. Confirm `"earth"` returns. The dirty marker is intentionally conservative and remains after undo/redo once an edit has occurred.
6. Press Ctrl+R. Confirm the success dialog says LibLR1 reparsed the candidate completely, the banner disappears, and writer-backed commands become enabled.
7. Click Edit > Binary Diff. Confirm source and candidate are both 17 bytes and the first difference is `0xA`; dismiss the dialog.
8. Press Ctrl+Shift+S and save only to `C:\Users\Dust Storm\Code\Lego Racers\LR1BinaryEditor\artifacts\manual-gui-acceptance\output\editable-edited.CDB`.
9. Confirm the dirty `*` clears. Close the tab; no save prompt should appear.
10. Reopen `output\editable-edited.CDB`. Confirm it is `ValidSemantic`, writable, and contains `"earth"`.
11. Recheck the SHA-256 of `editable-valid.CDB`; it must remain `AF9F863C92A8554D5E9CF373659D61896EC76017856B51720EB8FF5F23047B8F`.

Expected: edits are gated until canonical reparse succeeds, binary diff identifies the change, Save As writes only the disposable target, and reopen preserves the edited value.

### 4. Unknown token, issue navigation, and recovery to writable

1. Open `unknown-property.ADB`.
2. Confirm the text contains a `0x27` data block and one `0x40` line.
3. Confirm the yellow banner reports `InspectionOnly`, tokenized encoding, `UnrecognizedProperty`, token `0x40`, and decompressed offset `0x2`.
4. Confirm Save, Save As, and Export JSON are disabled while Validate remains enabled.
5. Press Ctrl+R. Dismiss the validation result and confirm the caret/focus moves to the `0x40` line.
6. Delete only the line containing `0x40`, leaving the `0x27` block and braces intact.
7. Confirm the dirty marker and `Candidate needs validation` banner appear.
8. Press Ctrl+R. Confirm the validation success dialog, hidden banner, `ValidSemantic` status, and re-enabled Save, Save As, and Export JSON.
9. Save As `C:\Users\Dust Storm\Code\Lego Racers\LR1BinaryEditor\artifacts\manual-gui-acceptance\output\unknown-recovered.ADB`.
10. Close and reopen that output. Confirm it remains `ValidSemantic` and writable.
11. Confirm the original `unknown-property.ADB` SHA-256 remains `48485BABE4356B0C26100D90BBD4EC2F0FA9C47C88411A0DB599C0CEAE8DEFDE`.

Expected: the failing token ID and offset are actionable, writers remain disabled while the token exists, and removing it transitions the same document back to writable.

### 5. Exact read-only fallback for unsafe decompression

1. Open `unsafe-decompression.CDB`.
2. Confirm the editor shows exactly one hex row beginning `00000000  13 00 01`.
3. Confirm the banner reports `InspectionOnly`, `Unregistered`, and `LibLR1 could not produce a safely decompressed token stream.`
4. Try typing in the editor and confirm the text does not change.
5. Confirm Save, Save As, Validate, and Export JSON are disabled.
6. Confirm the fixture SHA-256 remains `8EE0856CE51D239DD3D62A47D4FBD42F882E4C269AADE15A819A96A5237B2023`.

Expected: all three source bytes remain visible exactly, with no token compilation or writer route available.

### 6. Current JSON export and import

1. Select the reopened `output\editable-edited.CDB` tab.
2. Press Ctrl+E and export to `C:\Users\Dust Storm\Code\Lego Racers\LR1BinaryEditor\artifacts\manual-gui-acceptance\output\current-export.json`.
3. Confirm the JSON file exists and contains `"format": "CDB"`, `"rootType": "LibLR1.CDB"`, a nonempty `"sourceData"`, and a `"data"` object.
4. Press Ctrl+I and import `output\current-export.json`.
5. Confirm a new dirty tab opens, contains `"earth"`, reports `ValidSemantic`, and has writer-backed commands enabled.
6. Close the imported tab and choose Don't Save.

Expected: current JSON uses a validated source baseline and imports through a canonical temporary LibLR1 write/reopen cycle.

### 7. Intentional legacy JSON rejection

1. Press Ctrl+I and choose `legacy-no-sourceData.json`.
2. Confirm no document tab is created.
3. Confirm the error dialog says: `The JSON file is missing the validated sourceData baseline required for safe import.` The UI may display backticks around `sourceData`.

Expected: legacy JSON lacking `sourceData` is rejected explicitly rather than being guessed into a model.

### 8. Multiple tabs and close/save prompts

1. Open `corpus-valid.CDB`, `output\prompt-test.CDB`, and `unknown-property.ADB`; confirm each has an independent tab.
2. Select `output\prompt-test.CDB`, change `"world"` to `"earth"`, and click that tab's close button.
3. Confirm the Save Changes dialog offers Save, Don't Save, and Cancel. Choose Cancel and confirm the tab and dirty edit remain.
4. Click close again, choose Don't Save, and confirm the tab closes.
5. Reopen `output\prompt-test.CDB`; confirm it still contains `"world"`.
6. Change `"world"` to `"venus"`, click close, choose Save, and accept the successful validation dialog if shown.
7. Reopen `output\prompt-test.CDB`; confirm it contains `"venus"` and is writable.
8. With at least one other dirty tab open, close the application window. Choose Cancel at one prompt and confirm shutdown stops. Close again and use Don't Save for disposable changes until the application exits.

Expected: tabs do not share state, every dirty close is mediated by a three-choice prompt, Cancel preserves work, Don't Save discards it, Save writes only the disposable working file, and window shutdown stops on Cancel.

### 9. Folder navigation

1. Relaunch with the exact launch command.
2. Click the navigation-pane folder button and select `C:\Users\Dust Storm\Code\Lego Racers\LR1BinaryEditor\artifacts\manual-gui-acceptance`.
3. Confirm the tree shows supported fixtures, the `output` folder, and both JAM files with file-type icons.
4. Expand `output`, double-click `prompt-test.CDB`, and confirm the existing/opened tab is selected rather than duplicated on a second double-click.
5. Select tree items and confirm the navigation status line shows their concrete filesystem or archive paths.
6. Click Refresh and confirm the tree remains usable and reflects output files created earlier.

Expected: folder traversal, supported-file filtering, double-click open, duplicate suppression, status paths, and refresh work from the prepared fixture root.

### 10. JAM browse, entry edit, validation, and disposable repack

1. In the navigation tree expand `output` > `disposable-working.JAM` > `GAMEDATA`.
2. Double-click `ENTRY.CDB`. Confirm a tokenized tab opens with `"world"`, is `ValidSemantic`, and is writable.
3. Replace `"world"` with `"earth"`. Confirm the dirty/needs-validation gate, then press Ctrl+R and confirm successful reparse.
4. Press Ctrl+S. Do not use Save As. Confirm the dirty marker clears; this writes the extracted entry and repacks only `output\disposable-working.JAM`.
5. Close Binary Editor fully. Relaunch, select the manual acceptance folder, expand the same working JAM, and reopen `GAMEDATA\ENTRY.CDB`.
6. Confirm the entry now contains `"earth"` and is writable.
7. In PowerShell confirm the working archive changed while the pristine archive did not:

   ```powershell
   Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\Users\Dust Storm\Code\Lego Racers\LR1BinaryEditor\artifacts\manual-gui-acceptance\disposable-pristine.JAM'
   Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\Users\Dust Storm\Code\Lego Racers\LR1BinaryEditor\artifacts\manual-gui-acceptance\output\disposable-working.JAM'
   ```

8. Confirm the pristine hash is still `998D75E6880A39ECE392763A8E6ED5981A8D9BD3835155C46F551607B75F15BB`; the working hash should differ after the edit.

Expected: the tree browses LJAM contents, entry edits use normal LibLR1 gating, and only the disposable working archive is repacked.

### 11. Temporary-file behavior and final source-integrity check

1. Close Binary Editor fully.
2. Inspect the validation and JSON temporary directories:

   ```powershell
   Get-ChildItem -LiteralPath "$env:TEMP\LR1BinaryEditor\validation" -File -ErrorAction SilentlyContinue
   Get-ChildItem -LiteralPath "$env:TEMP\LR1BinaryEditor\json" -File -ErrorAction SilentlyContinue
   Get-ChildItem -LiteralPath "$env:TEMP\LR1BinaryEditor\JAM" -Directory -ErrorAction SilentlyContinue | Where-Object Name -Like 'disposable-working_*'
   ```

3. Confirm validation and JSON candidate files created during this run were removed. A `disposable-working_<guid>` JAM extraction directory is currently expected to remain after exit; record it in Notes as the known JAM-session cleanup limitation.
4. Re-run the installed-original SHA-256 command from the safety section and confirm it still returns `C3C57C439ECBC4FD17286F4B1A9994C7DA435E88C48F739F0522E5C9C60AE7D3`.

Expected: short-lived validation/JSON files are cleaned, the known JAM extraction-session residue is visible and documented, and the installed source remains unchanged.
